gleam-zig is an unofficial backend for the Gleam compiler that emits readable Zig and builds it into a dependency-free static executable, no VM, no garbage collector. Same parser, same type checker as official Gleam; a different machine underneath.

From a Gleam file to a native executable

There are no released binaries yet, you build the compiler fork from source. You need Rust, Python 3 (for the test harness), and ~5 minutes.

# the workspace expects sibling checkouts (compiler fork + stdlib fork)
git clone https://github.com/escherize/gleam-zig-workspace workspace
cd workspace
git clone https://github.com/escherize/gleam-zig gleam
git clone https://github.com/escherize/gleam-zig-stdlib gleam-stdlib

# zig 0.16.0 is fetched automatically on first run (manual install optional, below)
mkdir toolchain && cd toolchain
curl -O https://ziglang.org/download/0.16.0/zig-aarch64-macos-0.16.0.tar.xz
tar xf zig-aarch64-macos-0.16.0.tar.xz && cd ..
export GLEAM_ZIG=$PWD/toolchain/zig-aarch64-macos-0.16.0/zig

# build the compiler (this is the whole Gleam compiler, plus the zig backend)
cd gleam && cargo build -p gleam && cd ..

Or skip the project entirely. A single .gleam file exports straight to a binary, the compiler scaffolds a throwaway project around it (point GLEAM_ZIG_STDLIB at the stdlib fork, or run anywhere below a gleam-stdlib/ checkout):

# write one file, get one native binary
../gleam/target/debug/gleam export zig-executable fizzbuzz.gleam
./fizzbuzz

# the ray tracer's single source file works the same way, byte-identical image
../gleam/target/debug/gleam export zig-executable raytracer.gleam --out rt && ./rt > out.ppm

Point a Gleam project at the target and run it. The stdlib fork is a path dependency for now:

# gleam.toml
target = "zig"

[dependencies]
gleam_stdlib = { path = "../gleam-stdlib" }
# run in place (debug build, every run is leak-checked at exit)
../gleam/target/debug/gleam run

# or build a standalone ReleaseFast binary
../gleam/target/debug/gleam export zig-executable --out app
./app

# cross-compile the same project from the same machine
../gleam/target/debug/gleam export zig-executable --target-triple x86_64-linux --out app-linux

On first use of a zig-target command the compiler fetches and sha256-verifies the pinned Zig 0.16.0 into gleam's cache, no setup step. GLEAM_ZIG remains an explicit override (CI, hermetic setups), and a zig on PATH reporting exactly 0.16.0 is used as-is.

Fails loud. Anything the backend can't compile panics at build time with the construct named, nothing is silently mistranslated. That property is what makes the verification below meaningful.

A third backend, held to the official two's standard

Gleam officially compiles to Erlang (the BEAM) and JavaScript. gleam-zig is an unofficial fork adding a third machine: native code, via Zig. It reuses Gleam's own front-end, the same parser and type checker, so a program that type-checks officially type-checks here. What changes is everything underneath:

The honest headline: this target wins footprint and deployment on every measured workload, using 1.5x to 69x less memory than node and the BEAM, in a single dependency-free file. The spread is wide because it depends on how much the program allocates: the scalar workloads sit near 1 MB against 50 to 83 MB, while binary trees holds millions of live refcounted records and wins by only 1.5x. After the unboxing, borrowing, and liveness work, it wins the compute too. The scoreboard, method and caveats included, is in benchmarks.

See where every number comes from

What moved the needle, in order:

  • unboxed scalars and a raw native ABI
  • record and tuple reuse with borrowed field access
  • killing an mmap-per-allocation scratch allocator
  • a borrowed parameter ABI
  • capacity-tracked in-place string append
  • per-clause last-use moves
  • self-recursive borrowing: a greatest-fixpoint inference that lets recursion pass references without counting
  • inline field storage for small records
  • a flat record ABI that keeps scalar records in registers
  • a HAMT for dictionaries

Each one was verified against the full corpus under the leak gate before it landed. Every row is now a win on CPU and on memory, binary trees included, though that is the narrowest margin at 1.5x. The dictionary row was a 16x loss before the HAMT landed: an insertion-ordered assoc list against two real hash maps. It now finishes in under 0.01 s. The caveats that remain are semantic rather than performance: integers are i64 rather than bignums, and hash iteration order is unspecified (it now matches erlang's, where the assoc list happened to match V8's).

Three layers, and the middle one is Gleam compiling itself

There is no VM to document. Compiled modules lean on a small prelude, the standard library is mostly Gleam source compiled by this same backend, and only a thin externals core is hand-written Zig.

prelude.zig1,481 lines
The whole runtime: the uniform Value union, reference counting (dup/drop, last-use moves, in-place cons reuse), lists, records, strings, bit arrays, panics, and the debug-mode leak gate. Compiled into every binary; nothing links at runtime.
gleam_stdlib, self-hosted19 modules
The standard library's pure bulk, list, result, option, order, pair, set, folds and sorts and Result plumbing, is Gleam source compiled by this compiler. It runs Gleam's actual logic, not a reimplementation.
gleam_stdlib.zig, the externals core77 fns · 660 lines
The only hand-written layer: Zig implementations of the @external functions the stdlib bottoms out in, string codepoints, float formatting, parsing, I/O. This is the one place a bug could be silent; everything above it fails loud. Sibling forks cover simplifile, argv, envoy, and gleam_native (threads, TCP, time).

How values are represented

Every polymorphic value is one 32-byte tagged union, Value, mirroring the dynamic representation of the JS target: ints and floats inline, strings/lists/tuples/records as reference-counted pointers. Since the unboxing pass, Int/Float/Bool expressions and locals skip the union entirely and compile to raw i64/f64/bool; functions whose whole signature is scalar get a native raw ABI (that's the native$fib in the hero panel) plus a boxed wrapper for polymorphic callers.

A custom type compiles to a name-tagged record, and an exhaustive case compiles to sequential checks that end in unreachable, exhaustiveness is the Gleam type checker's proof, carried into the emitted code:

shape.gleam
pub type Shape {
  Circle(radius: Float)
  Rect(width: Float,
       height: Float)
}

pub fn area(shape: Shape) -> Float {
  case shape {
    Circle(r) -> 3.14159 *. r *. r
    Rect(w, h) -> w *. h
  }
}
shape.zig: emitted, verbatim
fn @"borrowed$area"(@"v$shape": Value) Value {
    c0: {
        if (!(P.recordHasName(@"v$shape", "Circle"))) break :c0;
        const @"v$r" = P.dup((@"v$shape").record.fields[0]);
        const @"r$0" = P.floatValue(
            ((3.14159 * (@"v$r").float) * (@"v$r").float));
        P.drop(@"v$r");
        return @"r$0";
    }
    c1: {
        if (!(P.recordHasName(@"v$shape", "Rect"))) break :c1;
        // … same shape for Rect …
    }
    unreachable; // exhaustiveness: the type checker's proof
}

// the owned wrapper public callers see:
pub fn @"area"(@"a$0": Value) Value {
    const result = @"borrowed$area"(@"a$0");
    P.drop(@"a$0");
    return result;
}
plate 02emitted by the fork at c6b902177; the Rect clause body is elided for width, otherwise verbatim

Worth saying plainly: variants are not per-type Zig tagged unions, and Result is not mapped to Zig error unions, Ok/Error are plain records like every other variant. The uniform representation is what lets one prelude serve all types; per-type unboxed layouts are future work, not current truth.

Where the memory goes: the list-churn benchmark peaks at 236.7 MB with counting disabled and 2.3 MB with Perceus reference counting on, same program, same output. Release builds add object pooling; debug builds trade speed for the leak gate.

Every number on this page has an oracle

The method: run every test program twice, once with the official Gleam compiler (the JavaScript target, on node), once compiled to a native binary by this fork, and diff the normalised stdout. Pass means byte-identical, and deliberate crashes must match too. The exception is programs whose output has no defined order, the ones using gleam/dict, gleam/set, or randomness: hash iteration order is unspecified per target, so those are held to a clean exit instead of a byte diff.

The tri-target demo

A ~200-line ray tracer runs unchanged on all three targets and produces byte-identical images (md5 7a452dda…): native 0.08 s / 5.7 MB in a 411 KB binary, node 0.17 s / 66 MB, BEAM 0.35 s / 83 MB, all CPU time. Three days of optimization took the native render from 0.66 s to nearly twice V8’s speed, at a tenth of the memory. The story is written up in "A ray tracer in Gleam, but 4.7× faster".

The soft spot, named: the 77-function hand-written externals core is the only layer that can be silently wrong, everything else fails loud at compile time. Differential fuzzing aimed at exactly that layer has not run yet planned; the corpus and the leak gate are the current evidence.

The output is Zig you can read, and import

A build emits one .zig file per Gleam module plus the prelude, laid out as an ordinary Zig source tree. The generated entrypoint consumes it the same way your code can:

// what `gleam run --target zig` itself generates and runs:
const std = @import("std");
const P = @import("prelude.zig");
const app = @import("my_project/app.zig");

pub fn main(init: std.process.Init.Minimal) void {
    P.process_args = init.args;
    P.process_environ = init.environ;
    P.drop(app.@"main"());    // any pub fn: Value in, Value out
    P.leakCheckExit();          // debug builds, or GLEAM_ZIG_LEAK_GATE=1
}
  • Public functions use the boxed ABI, take and return P.Value; construct arguments with P.intValue, P.copyString, and friends from the prelude
  • Ship one file instead: gleam export zig-executable produces a static ReleaseFast binary; --target-triple cross-compiles it. Compilation for linux x86_64/aarch64, windows, and macos is verified from one machine, the windows binaries themselves have never been run (see limits)
  • Or ship one source file: gleam export zig-source emits the whole project, every module, the native files, the inlined runtime, and an entrypoint, as one .zig file anyone can zig run with no gleam installed. The ray tracer's single file produces the byte-identical image

Also stated plainly: there is no external production consumer yet, no third-party Zig project calling compiled Gleam in anger. The entrypoint above is the real, working consumption path; a packaged library story is future work.

What it is, and what it isn't

gleam-zig is experimental but real: a fork of the actual Gleam compiler, a self-hosted standard library, a leak-proven memory system, and a corpus that matches the official compiler, byte-for-byte wherever output order is defined. It is not a finished product, and these edges are deliberate, read them like a build log:

WARNIntegers are i64Wrapping 64-bit ints, no bigint. The one semantic divergence from the BEAM's arbitrary precision, stated here, not buried.
WARNNo OTPBEAM processes, supervisors, and the actor model don't exist here. gleam_native gives OS threads, sleep, and blocking TCP, for computational Gleam, not concurrent systems.
WARNMutual recursion is stack-boundedSelf tail-calls compile to loops; mutually recursive functions ride the native stack (JS-target parity).
WARNUnicode is approximateCase and trim are ASCII; "graphemes" segment by codepoint. Real casing tables and UAX-29 need data Zig's std doesn't carry.
INFODict iteration order is unspecifiedA 32-way hash array mapped trie, five hash bits per level. Iteration follows hash order, which matches erlang and differs from the JavaScript target.
INFOStrings copyConstruction and slicing copy buffers (a deliberate naive-RC decision); bit arrays already share buffers, strings will follow.
INFOBit arrays are byte-alignedSub-byte segments and utf16/32 segments are unsupported and fail loud at compile time.
INFOWindows is untestedBinaries cross-compile for windows, but argv FFI is posix-only and no CI runner exercises them.
INFOFFI-backed packages need shimsHex packages whose externals target Erlang/JS need a small Zig implementation; pure-Gleam packages just work.
