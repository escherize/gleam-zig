String building — zig 28× node, 11× the BEAM

200,000 pieces folded onto one accumulator. The workload every templater, serializer, and logger is secretly made of.

zig
0.01 s19 MB
node
0.28 s118 MB
erlang
0.11 s123 MB
the benchmark
let joined =
  list.fold(parts, "", fn(acc, x) {
    acc <> x <> ";"
  })
the hot path — runtime, in-place append
// acc reaches here with refcount 1, so:
if (need <= have) {
    // room in the buffer: just write
    @memcpy(out[a.len..], b);
} else {
    // double the buffer, capacity in the header
    while (new_words < need) new_words *= 2;
    realloc(...); grown[0] = 1 | (new_words << 32);
}

Why it's fast: two pieces had to land together. The runtime tracks buffer capacity in the string header and appends in place when the left operand is unshared — but that only fires if the accumulator actually reaches the append with refcount 1. list.fold uses its accumulator once in each of two case clauses, which naive analysis reads as two uses. Per-clause liveness (only one clause runs) approves the transfer, the refcount stays 1, and 200k appends become an amortized-linear write instead of 200k full copies. Node's string concat is rope-optimized and still loses 6×.

Dictionary — zig 7× node, 11× the BEAM

Ten thousand keys inserted into a map, then every one looked up again. The workload every real program does — indexing data — and the worst thing this target currently does.

zig
<0.01 s7 MB
node
0.07 s78 MB
erlang
0.11 s87 MB

How it was won: until this row appeared on the board, gleam/dict on this target was an insertion-ordered association list — every insert scanned for an existing key and every get scanned to find one, so the workload was O(n²) against two real hash maps. No codegen work could have rescued that; it was a data structure that had not been written. It is now a hash array mapped trie, the same structure the JavaScript target uses: five hash bits per level, 32-way branching, so a lookup touches three or four nodes and an insert copies one node per level instead of the whole dict.

The nodes are ordinary reference-counted values, so the runtime's existing memory discipline covers the trie with no new lifetime rules — the leak gate checks it on every corpus run like everything else. One semantic consequence, stated plainly: iteration order is hash order now rather than insertion order. That order was always unspecified and differs on all three targets; the new one happens to agree with erlang where the old one happened to agree with V8.

Ray tracer — zig 2× node, byte-identical output

The tri-target demo: 320×240, three bounces, and the PPM output is md5-identical on all three machines — this row is also a correctness proof.

0.08 s6 MB

0.17 s33 MB

0.33 s74 MB
the hot shape — vec math
fn dot(a: Vec, b: Vec) -> Float {
  a.x *. b.x
  +. a.y *. b.y
  +. a.z *. b.z
}
emitted — borrowed reads, no refcounts
fn borrowed$dot(a: Value, b: Value) Value {
    return P.floatValue(
        ((a).record.fields[0]).float * ((b).record.fields[0]).float
      + ((a).record.fields[1]).float * ((b).record.fields[1]).float
      + ((a).record.fields[2]).float * ((b).record.fields[2]).float);
}

Turn the knobs: this render measured across resolutions to 8K and bounces to 10.

Why it's fast — eventually: this number took six optimizations and one wrong diagnosis. The hot path is Vec record math; the wins came from borrowed field reads (no refcount round-trip per v.x), in-place record reuse in pattern-matched constructions, a borrowed parameter ABI for the vector helpers, and — the day's embarrassment — discovering that a third of the runtime was 230,000 mmap syscalls from a scratch allocator, misdiagnosed the previous night as "output writes". Inline field storage for small records closed the final gap past V8.

Coin change — zig 7× node, 3× the BEAM

Naive recursive counting, ~100 million calls — list pattern-matching and recursion, the BEAM's home turf. It was a loss row until self-recursive borrowing.

zig
0.12 s1.2 MB
node
0.84 s49 MB
erlang
0.45 s73 MB
ways.gleam
fn ways(amount: Int, coins: List(Int)) -> Int {
  case coins {
    _ if amount == 0 -> 1
    _ if amount < 0 -> 0
    [] -> 0
    [c, ..rest] ->
      ways(amount - c, coins)
      + ways(amount, rest)
  }
}
emitted, condensed — zero refcount ops
fn borrowed$ways(amount, coins: Value) Value {
    if (amount.int == 0) return one;   // raw guard
    if (amount.int < 0)  return zero;
    ...
    // rest borrows the spine: no dup, no drop
    const rest = P.listValue(coins.list.?.tail);
    return borrowed$ways(a2, coins)  // self, borrowed
         + borrowed$ways(amount, rest);
}

Why it flipped: borrow inference runs to a greatest fixpoint — recursion is allowed to justify its own borrows, which is sound because call frames nest inside the outermost owner's lifetime. With coins passing itself down borrowed and rest borrowing the list spine out of the subject, the recursion performs zero reference-count operations per call. That took it from 2.53 s (three days ago) through five separate optimizations to 0.28 s — past the BEAM JIT that owned this row.

Vector records — fastest of all three targets

Ten million iterations of allocate-two-records, read-six-fields — pure allocation churn, kept as the honest stress test of the memory system.

zig
0.03 s1.2 MB
node
0.05 s50 MB
erlang
0.13 s73 MB
the loop body
let w = add(v, scale(v, 0.5))
loop(n - 1, v, acc +. dot(w, w) *. 0.000001)
emitted — the allocations that remain
const w = bc: {
    // scale allocates a pooled Vec (fields inline)
    const t = borrowed$scale(v, P.floatValue(0.5));
    // add reads it borrowed, allocates the result
    const r = borrowed$add(v, t);
    P.drop(t);  // back to the pool
    break :bc r;
};

Why it stopped losing: the JITs escape-analyze these temporaries into registers, so for weeks this row was the honest loss on the board. The flat record ABI answers it directly: a single-constructor record whose fields are all scalars now travels as a zig struct inside its module, so add/scale/dot compile to register arithmetic with no allocation at all — 0.17 s to 0.03 s, past both JITs. What stays boxed is what the rule excludes: multi-constructor types, records holding strings or lists, anything generic.

Binary trees — zig 1.4× node; memory still the loss

Build a full depth-21 binary tree four times and walk it. Millions of multi-constructor records allocated, pattern-matched, and released — the allocation benchmark, and the row that drove the most recent runtime work.

zig
—1.03 GB
node
0.96 s756 MB
erlang
0.46 s834 MB

What changed: counting allocations by shape found that half of every record this benchmark allocates — 81,920 of 163,830 — is a Leaf, a nullary constructor carrying no payload at all. A full binary tree has more leaves than internal nodes, so the majority allocation was a 120-byte heap record representing nothing. Nullary constructors are constants, so each variant now gets one immortal shared value instead. Peak memory fell from 2.0 GB to 1.03 GB, exactly the predicted half.

Why the time column was blank here yesterday: the figure this row published (1.07 s) stopped reproducing, and the honest move was to show a gap rather than restate a number we could not stand behind. Chasing it found a real regression: the runtime’s two environment gates — the leak check and the pooling switch — were each scanning the whole process environment per call, and both sit on the allocation path. At 16.8 million records this benchmark was spending over a billion string comparisons deciding, repeatedly, that nothing had changed. Resolving each gate once took depth 21 from 42.5 s back to 0.70 s. The ray tracer, which had drifted the same way, returned to 0.08 s with byte-identical output.

Still open: memory. 1.03 GB against node’s 885 MB and the BEAM’s 834 MB is the one number on this page where zig loses outright, and it is structural: a live depth-21 tree is 4.2 million Node records at 120 bytes each. The 56-byte header is the target — a comptime name-hash tag, labels folded into the tag word, or pooling by arity — but this row is also the standing reminder to measure first: the last guess about where record cost sat was wrong by 2×.

Method

  • Correctness before speed: every workload's output is byte-diffed across targets before any timing counts — the ray tracer's PPM is md5-identical on all three; every zig run in the differential harness is also leak-checked at exit
  • What runs: zig as a ReleaseFast static binary; node 22 and erl (OTP 27) invoked directly on built output, no CLI wrapper in the timed path; BEAM figures are CPU time with the ~1 s VM boot excluded (wall time would flatter zig). Node’s peak-memory figures include the runtime’s own footprint, because that is what the machine actually pays — an empty node process is already ~38 MB here, so any figure below that is not measuring a real process
  • How measured: /usr/bin/time -l (user CPU, peak memory footprint), best of 3, Apple M-series, compiler fork ff1fd2bcd. The shipped-artifact column is the exported binary (zig), the whole JS build tree (node) and the compiled BEAM files (erlang) — for node that includes gleam_stdlib and the prelude, without which the emitted module will not run
  • Sources: each benchmark is a one-file Gleam program in examples/benchmarks/ of the workspace repo (the ray tracer is examples/demo/raytracer/); the corpus gate (119 programs byte-identical, 0 failures, leak-clean) re-runs on every push. Experiment ledgers live in examples/benchmarks/results.tsv
  • What's NOT here: no warmup games (JITs get their natural single-run behavior, same as the binary), no per-target tuning, no cherry-picked coin denominations — and when a row loses, it stays on the board
  • When a number stops reproducing: it gets treated as a bug until proven otherwise. The binary-trees and ray-tracer rows drifted ~40× and ~100× from their published figures; the cause was a real allocation-path regression, not a bad measurement, and both rows returned to their published values once it was fixed. A figure on this page that cannot be reproduced by the command next to it is a defect report
